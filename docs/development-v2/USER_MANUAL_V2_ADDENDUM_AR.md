# دليل استخدام ميزات Development v2

## 1. قبل البدء

تظهر الميزات الجديدة داخل نسخة التطوير. استخدم حساباً بدور Admin أو Project Manager. التحليل يعمل محلياً، لكن يجب أن يكون Ollama وعامل Queue قيد التشغيل.

### 1.1 ما الذي تغيّر؟

- أصبح بإمكان المشروع استخدام تقدم المهام التقليدي أو تقدم مراحل موزونة.
- يمكن إدخال مشروع قائم بكامل وضعه الحالي بدلاً من معاملته كمشروع جديد.
- أصبحت المتطلبات منظمة في شجرة فئات ومجموعات وعلاقات.
- يمكن استخراج متطلبات مرشحة من كراسة PDF/DOCX محلياً ومراجعتها قبل اعتمادها.

## 2. إنشاء خطة مراحل ومعالم

1. افتح المشروع ثم انتقل إلى قسم الخطة/الجدول الزمني.
2. اختر «تحرير الخطة».
3. أضف مرحلة واكتب الاسم والبداية والنهاية والوزن ومعايير الإكمال.
4. أضف Milestones داخل المرحلة وحدد إن كان كل واحد «بوابة تسليم» إلزامية.
5. كرر المراحل حتى يصبح مجموع الأوزان 100%.
6. احفظ الخطة دفعة واحدة.

### 2.1 تفسير التقدم

- مرحلة مكتملة يدوياً: 100%.
- مرحلة عاملة: نسبة مهامها المكتملة من المهام غير الملغاة.
- مهام مكتملة وبوابة إلزامية مفتوحة: 99% و«بانتظار الاعتماد».
- تقدم المشروع: مجموع تقدم كل مرحلة مضروباً في وزنها.

### 2.2 تفسير الصحة

| الحالة | المعنى العملي |
|---|---|
| في المسار | المرحلة نشطة ولا توجد إشارة تأخر. |
| تحتاج متابعة | توجد أعمال مفتوحة أو بوابة تحتاج قراراً قريباً. |
| متأخرة | انتهى موعد المرحلة أو المعلم دون إكمال. |
| مكتملة | أغلقت المرحلة ومعالمها الإلزامية. |

### 2.3 ربط المهام والمتطلبات

- عند إنشاء أو تعديل مهمة، اختر «المرحلة الأساسية» إن وجدت.
- عند إنشاء أو تعديل متطلب، حدد المراحل والمعالم المرتبطة.
- لا يمكن اختيار مرحلة من مشروع آخر.
- لإزالة كل الروابط، ألغ تحديد جميع الخيارات ثم احفظ.

## 3. إدخال مشروع قائم

من قائمة المشاريع اختر إدخال مشروع قائم، ثم أكمل الخطوات التالية:

1. المشروع والعميل والفريق.
2. تاريخ البداية الحقيقية وتاريخ الانتقال إلى Project Desk.
3. المراحل السابقة والحالية والمستقبلية وأوزانها.
4. المعالم السابقة والقادمة.
5. المهام المفتوحة فقط؛ لا يلزم إعادة بناء كل التاريخ.
6. المخاطر والمشكلات القائمة.
7. المراجعة والاعتماد.

### 3.1 المرحلة التاريخية

يمكن تعليم مرحلة سابقة كمكتملة من دون إنشاء مهامها القديمة. استخدم وصفاً ومعايير إكمال واضحة، وأدخل المعالم التاريخية المهمة فقط.

### 3.2 Snapshot الانتقال

بعد الاعتماد يحفظ النظام لقطة غير قابلة للتعديل تتضمن وضع المشروع وخطته وتقدمه ومن اعتمدها. الغرض منها إثبات نقطة البداية داخل النظام، لا استبدال محاضر أو ملفات الماضي.

### 3.3 Checklist بعد الإنشاء

ارفع بعد الإنشاء:

- آخر إصدار معتمد من كراسة المتطلبات.
- العقود أو نطاق العمل الضروري.
- محاضر القرارات السابقة المهمة.
- ملفات التسليمات السابقة.
- سجل المخاطر أو المشكلات إن كان موجوداً خارج النظام.

## 4. تنظيم المتطلبات

### 4.1 الهيكل

```text
الفئة
  المجموعة
    المتطلب
```

مثال:

```text
الأمن
  المصادقة
    تسجيل الدخول
    المصادقة الثنائية
  الصلاحيات
    أدوار المستخدمين
```

### 4.2 الأنواع

اختر النوع بشكل مستقل عن الفئة: وظيفي، تقني، غير وظيفي، أمني، بيانات، تكامل، أعمال.

### 4.3 إدارة الشجرة

- استخدم الأسهم لترتيب الفئات والمجموعات.
- انقل مجموعة إلى فئة أخرى من قائمة «نقل إلى فئة».
- استخدم «دمج مع» لجمع مجموعتين؛ تنتقل المتطلبات ولا تضيع.
- تبقى المتطلبات القديمة في «غير مصنف» حتى تنقلها.

### 4.4 العلاقات

من صف المتطلب اختر المتطلب الهدف ونوع العلاقة ثم «ربط»:

- يعتمد على: لا يبدأ/يكتمل منطقياً قبل الهدف.
- يكمّل: يضيف نطاقاً متكاملاً.
- يفصّل: يشرح متطلباً أوسع.
- يتعارض مع: توجد قاعدة أو نتيجة متناقضة.
- مكرر: نفس القصد تقريباً.
- يستبدل: نسخة أو قرار أحدث.
- مرتبط بـ: علاقة عامة لا تحمل دلالة تنفيذية قوية.

يمنع النظام الربط بالنفس والربط بمشروع آخر ودورات «يعتمد على».

### 4.5 مؤشرات التغطية

يعرض كل متطلب إن كان مرتبطاً بمهمة. استخدم المؤشرات لاكتشاف:

- متطلبات بلا تنفيذ.
- مجموعات منخفضة التغطية.
- تعارضات غير محسومة.
- تبعيات قد تعطل مرحلة لاحقة.

## 5. إعداد المحرك المحلي

يدير Admin الإعدادات من «إعدادات النظام > الذكاء الاصطناعي المحلي».

| الإعداد | القيمة الموصى بها |
|---|---|
| التفعيل | مفعّل |
| التحليل التلقائي | متوقف حتى اعتماد سياسة الفريق |
| النموذج | `qwen3:8b-q4_K_M` |
| السياق | 8192 |
| حد الصفحات | 300 |

تعرض بطاقة الحالة:

- اتصال Ollama.
- وجود النموذج.
- اسم GPU والذاكرة المتاحة.
- Poppler وتحويل PDF إلى صور.
- Tesseract ولغتا `ara` و`eng`.
- تأكيد أن endpoint محلي وأن السحابة غير مفعلة.

## 6. بدء تحليل كراسة

1. افتح المشروع ثم «كراسة المتطلبات».
2. ارفع إصدار PDF أو DOCX صالحاً وحدده كإصدار حالي عند الحاجة.
3. اختر الإصدار في لوحة التحليل.
4. اضغط «بدء التحليل المحلي».
5. تابع شريط الحالة؛ يمكنك مغادرة الصفحة لأن التنفيذ عبر Queue.

### 6.1 حالات التشغيل

| الحالة | ما الذي تفعله؟ |
|---|---|
| queued | انتظر عامل الطابور. |
| waiting_for_engine | شغل Ollama أو ثبت النموذج؛ لا تعِد الرفع. |
| extracting | يجري استخراج النص/OCR. |
| security_review_required | اطلب من Admin مراجعة التحذير. |
| analyzing | يحلل المقاطع محلياً بالتتابع. |
| merging | يدمج التكرار والعلاقات والأسئلة. |
| review_ready | ابدأ المراجعة البشرية. |
| approved | اكتملت عملية الاعتماد. |
| failed | اقرأ الخطأ المنقح، أصلح السبب ثم أعد. |
| cancelled | يمكن بدء run جديد عند الحاجة. |

### 6.2 إيقاف وإعادة

- «إلغاء» يوقف الاستمرار الآمن؛ لا يحذف الكراسة.
- «إعادة» تنشئ محاولة جديدة وفق قواعد البصمة والحالة.
- لا يبدأ النظام نسخة مطابقة مرة أخرى إذا كانت البصمة والنموذج والتعليمات متطابقة.

## 7. مراجعة Candidates

لا تعتبر النتيجة متطلباً قبل اعتمادها.

راجع لكل Candidate:

- الفئة والمجموعة والنوع.
- العنوان والوصف ومعايير القبول.
- الأولوية والعلاقات.
- الصفحة أو القسم/الفقرة والمقتطف.
- الثقة والأسئلة والغموض.

### 7.1 الإجراءات

- اعتماد: إنشاء المتطلب كما هو.
- تعديل واعتماد: تصحيح المحتوى والتصنيف ثم الإنشاء.
- رفض: حفظ قرار الرفض فقط.
- دمج: ضم Candidate إلى متطلب قائم.
- نقل: تغيير المجموعة قبل الاعتماد.
- تحويل إلى سؤال: حفظه كسؤال يحتاج إجابة.
- تحويل إلى مخاطرة: إنشاء مخاطرة بعد تأكيد المدير.
- اعتماد مجموعة: معاملة واحدة؛ إن فشل عنصر لا يعتمد أي عنصر منها.

### 7.2 قواعد مراجعة عملية

1. لا تعتمد ثقة مرتفعة وحدها؛ تحقق من المقتطف.
2. عدل العنوان ليكون قابلاً للاختبار لا مجرد نسخ فقرة.
3. افصل المتطلب المركب إلى أكثر من Candidate عند الحاجة.
4. لا تحول الغموض إلى افتراض؛ استخدم «سؤال».
5. راجع علاقات التعارض والاستبدال قبل الاعتماد الجماعي.

## 8. مقارنة إصدارات الكراسة

بعد تحليل إصدار جديد تظهر التصنيفات التالية:

- جديد.
- معدل.
- محذوف من الإصدار الجديد.
- متعارض مع قائم.
- يستبدل آخر.

يعرض النظام المهام والمراحل التي قد تتأثر. لا يحذف أو يعدل متطلباً معتمداً تلقائياً. يجب اتخاذ القرار ثم تحديث النطاق أو المهمة أو المرحلة يدوياً وبأثر تدقيق.

## 9. التنبيهات وتقارير PDF

- يعرض Dashboard المرحلة الحالية والمعلم القادم.
- تعرض قائمة المشاريع نفس الملخص المختصر.
- يتضمن PDF ملخص المراحل والأوزان والتقدم والصحة.
- تصل تنبيهات المعالم افتراضياً قبل 14 و7 و3 أيام وعند التأخر، ما لم تعطل تفضيلات المستخدم أو إعدادات النظام.

## 10. استكشاف الأعطال

### Ollama غير متاح

افتح تطبيق Ollama، ثم تحقق من الإعدادات. لا تغير عنوان endpoint. إذا لم يظهر النموذج نفذ:

```powershell
ollama pull qwen3:8b-q4_K_M
```

### OCR لا يقرأ العربية

تحقق من ظهور `ara` و`eng` في بطاقة الحالة. أعد رفع مسح أوضح إن كانت الصفحات منخفضة الدقة أو مائلة.

### التحليل بطيء

- هذا متوقع لكراسة كبيرة لأن المقاطع تحلل بالتتابع.
- لا تشغل أكثر من تحليل واحد على GPU 8GB.
- لا تغلق Ollama أو عامل Queue.
- يمكن خفض context إلى قيمة معتمدة عند ضغط الذاكرة، لكن لا ترفعها عشوائياً.

### نتيجة غير دقيقة

ارفض أو عدل Candidate. لا تحاول «إجبار» النموذج عبر نص داخل الكراسة؛ تعليمات المستند تعامل كبيانات غير موثوقة.

## 11. طريقة العمل النموذجية

```text
إنشاء/إدخال المشروع
 -> اعتماد خطة المراحل
 -> رفع كراسة حالية
 -> تحليل محلي
 -> مراجعة Candidates
 -> اعتماد المتطلبات وربطها بالمراحل
 -> إنشاء المهام وربطها بالمتطلبات والمرحلة
 -> متابعة التقدم والبوابات والمخاطر
 -> تحليل الإصدار التالي ومراجعة الأثر
```

## 12. الخصوصية

- الكراسة لا ترسل إلى API سحابي.
- Ollama يستقبل النص المستخرج عبر loopback فقط.
- النموذج لا يقرأ ملفات أخرى.
- المراجعة البشرية إلزامية.
- ملفات OCR المؤقتة تحذف بعد التحليل وفق دورة التنفيذ.
